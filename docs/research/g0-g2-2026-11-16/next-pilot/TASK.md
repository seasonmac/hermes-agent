# 候选最小协作场景：跨 harness 接入契约的反例审查

状态：研究用任务包，尚未运行质量对照，也不是已批准的系统设计。选择软件工程作为首个候选，是因为当前已有可核验的真实代码/协议观察；不意味着软件任务总比量化或市场研究更适合多 Agent。

## 真实问题

拟议的独立协作模块需要接入 Hermes 和 Codex。请审查下列候选接入承诺，给出一个首版可以兑现的最小契约。不编写适配器，不调用现有业务服务，不借用未验证的 OpenClaw/DSH 能力。

候选提案（刻意包含待审查假设，不代表团队认可）：

1. submit(session, message, client_id) 在所有 harness 上天然幂等；网络超时后可以原样无限重试。
2. 每次 submit 都对应一个新的独立 step；忙时追加也不例外。
3. cancel 返回成功后，群聊立即展示已停止，且整个协作组都不会继续。
4. observer 重连与进程重启都用 resume，二者可以承诺相同恢复保证。
5. 用每条 turn.completed 的 usage 直接累加，可以得到协作组总费用。
6. 原生 interacted 事件足以证明对方收到并理解消息，也足以复原群聊中的协商正文。
7. 在本地测试通过便可以声明源码 HEAD 对应的所有部署版本都支持上述能力。

## 同一份证据

manifest.json 中的所有文件对各条件、各角色均可见。它们记录真实实测，但证据等级不同：Hermes 是既有服务上的真实模型，Codex G1 使用本机 fixture，原生协作 trace 来自真实模型。文档中的源码判断不自动升级为实测。

单 Agent 同时具有设计和反例审查职责。双 Agent 只分配注意力方向，不隐藏证据、不禁止角色交叉核对，也不指定单方必须接受另一方结论。

## 必须交付

- 对七项承诺逐项作“可承诺 / 需条件 / 当前不可承诺”判断，并引用具体证据。
- 描述三个反例的事件顺序：重复投递同时发生；B 忙时收到另一任务消息；取消请求后出现迟到结果。逐步写出可观察状态、任务归属和不能推出的结论。
- 给出最小补足要求，区分已有 harness 能力、独立模块必须承担的责任，以及应保留为未知的行为。不得用新治理角色或第三个大模型代替确定性收件/状态控制。
- 明确一个你曾经修正的判断，或说明审查未产生新的有效信息。不得为了展示协作而编造分歧。
- 最终交付最多 1,000 中文字，允许附状态表。正确保留未知优于没有证据的确定结论。

## 这里的“对等”

参与者可自行提出反例、拒绝缺乏证据的方案、要求澄清并提出替代方案；双方直接寻址。指定一个交付 Owner 只负责整理最终产物，不意味着它可以把别人的未经接受意见写成共识。测试不声称有平等进程所有权或完整去中心化治理。
