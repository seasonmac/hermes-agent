# G2 Token 增长复核

后续实测更新见[边界验证](boundary-validation/README.md)：三消息仍有8次用量增量、100,110总tokens；原生budget共享但非硬上限，冷恢复可重置。本文保留此前分析/校准的历史范围，不把不同任务的用量相除为优化倍数。

2026-11-16。本轮仅分析既有测试记录和本地源码，没有新增模型实验、安装或产品代码修改。

结论：**6.50 倍累计 tokens 是真实记录的合计，但不能解释为“多 Agent 架构必然贵 6.5 倍”。** 主要放大因素是多次模型续跑 × 每次较大的上下文；还发现实验未冻结技能目录，比较环境不一致。上一轮对实验控制不足的解释不够具体，需要据此收紧结论。

## 1. 先排除加总错误

双 Agent 六次试验各只有一个 root 与一个 peer；取每个线程最后一条累计 usage，再相加。对所有 12 个线程逐条复核：相邻累计值之差与 last_token_usage 一致。没有把每条累计快照重复求和，没有把缓存输入额外加到输入，也没有把 reasoning_output_tokens 再加到 output_tokens。六个失败或不可验真的初始 B 尝试不在 6.50 倍的分子里，它们另产生至少 694,002 主线程 tokens 的调试成本。

| 六次任务合计 | 单 Agent A | 双 Agent B | B/A |
| --- | ---: | ---: | ---: |
| 输入 | 199,871 | 1,311,024 | 6.56 |
| 其中缓存输入 | 96,768 | 1,058,944 | 10.94 |
| 非缓存输入 | 103,103 | 252,080 | 2.44 |
| 输出，含已报告推理输出 | 2,823 | 6,970 | 2.47 |
| 其中推理输出 | 522 | 411 | 0.79 |
| 输入 + 输出 | 202,694 | 1,317,994 | 6.50 |

额外总量 1,115,300 中有 1,111,153 来自输入，约 99.6%。新增输入中 86.6% 是缓存输入。B 的输入缓存命中比例约 80.8%，A 约 48.4%。**不能解释为生成了六倍长的答案，或进行了六倍推理。**

6.50 倍是所有请求累计量，不是某一个请求塞了 131 万上下文。重复的系统/工具/历史前缀仍进入累计输入计量，即使命中缓存。

没有实际账单或本模型费率，本次不推算金额。若按常见的输入/缓存输入/输出分项计价，需分别计算 `非缓存输入 × p_input + 缓存输入 × p_cache + 输出 × p_output`；具体订阅、额外计费规则及费率仍需另行核对。2.44 倍非缓存输入同样不是账单倍数。

## 2. 第一主因：一次小任务被展开为很多次模型调用

[逐次调用记录](g2/token-call-breakdown.json)显示：B 六组共有 **66 次独立 usage 增量**，root 41 次、peer 25 次。逐次增量均与 last_usage 相等，未把同值通知算成新调用。

| B 角色，六组合计 | 用量增量次数 | 输入 | 输出 |
| --- | ---: | ---: | ---: |
| root | 41 | 759,578 | 5,832 |
| peer | 25 | 551,446 | 1,138 |

以软件题第一组为例，root 七次请求的输入分别为 16,162、16,575、16,751、16,907、17,143、17,236、17,410；peer 四次为 21,863、22,094、22,205、22,343。root 合计 119,268，peer 88,773，任务总量 208,041；A 同题为 29,780。

这不是仅增加一次同伴审查。实际控制流包含创建同伴、读取更正、发送更正/意见、等待、回信和最终整合，模型在若干工具回执之后继续生成。六组记录到 6 次 spawn、19 次 send_message、19 次 wait_agent，另有读取材料等步骤。短小任务本身只需要很少推理，编排开销因此突出。

A 使用 ephemeral，未保留逐请求 rollout；其 exec 轨迹显示初步意见 → 读更正 → 最终答案，但公开流会省略部分内部事件。因此不能把“A 恰好 12 次模型请求”写成已经验证的事实，也不能做严格调用次数的因果分解。

### 等待的准确含义

Codex 的 wait_agent 在工具内部订阅输入活动并异步阻塞，并不是等待期间不断调用模型。[实现](/Users/season/workspace/github/codex/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs:73)。成本发生在工具返回后模型再次处理上下文，而非空闲等待的每一秒。

19 次 wait 后续请求合计 388,598 输入，其中 382,848 是缓存输入。这个数字只标记“发生在等待之后”的请求，**不是可以全部删除的浪费或节省预测**；其中包含读取有效意见、完成最终答案所必需的生成。当前记录也不足以把所有等待称为无效轮询。

## 3. 第二主因：运行环境没有冻结，技能目录明显不一致

[上下文检查](g2/context-audit.json)发现：

- 六个 B 的 peer 全部收到 **86 项技能目录**，该块为 **29,210 字符**。
- 六个 B 的 root 中五个只有 **4 项目录**，该块为 **2,123 字符**；market-B-2 的 root 也为 86 项。
- 同伴与主线程的基础指令文本均为 26,155 字符，除此之外还有角色、工具说明、权限等内容。这里的字符数不是精确 token 数。
- 典型 root 首次输入约 16.2k tokens，peer 约 21.8k；market-B-2 root 首次约 22.5k，后续约 29.4k–29.9k。

这证明即便请求使用同型号、同 reasoning effort、相同 CLI 基础参数，实际注入的环境仍不一致。原提示中的“Do not use skills”只是行为要求，**不等于删除技能目录**；也不是实际执行了 86 个技能。额外目录在多轮请求中继续增加输入及缓存输入。

该目录为何在不同启动和角色间变化，尚未定位到具体加载分支；不能贸然定为 Codex 的产品缺陷。A 没有完整 rollout，无法反推出六次 A 各自究竟收到多少技能。因此本轮无法计算环境完全一致时的准确倍数。

按每个 B 线程首个请求长度乘该线程请求数，得到 1,246,840，占实际输入 1,311,024 的 95.1%。这是长度层面的描述，**不等于证明这些 token 逐字相同或全都无用**。但与实际高缓存命中一起，足以说明“较大的初始上下文被多轮携带”远比任务材料持续膨胀更能解释主量级。

## 4. 第三因素：实验流程偏重，题目又过于简单

本轮每个小题都强制启动同等强度同伴并完成质疑/回应，还要求初步意见后再读取更正。它适合检查双向投递是否可运行，却不是最低成本的问题求解方式。全部答案达到粗粒度评分上限，额外协调没有在该量表体现收益。

此次验证是“同型号模型的原生委派关系内允许双向通信”，不是完整的独立对等协作运行时。不能据此宣布正式运行时的 Router、共享上下文、动态工作流会花同样成本。原始 A 为临时会话、修正后的 B 为持久会话；缓存冷热、目录加载和并行时机也没有被严格控制。墙钟上限和可见字数限制，不等于相同总 token 预算。

因此要保留两条不同结论：

1. **成立：**本次配置的小任务双 Agent 开销很高，且未观察到量表上的质量提升。
2. **不成立：**多 Agent 普遍没有收益，或者正式架构必然需要 6.5 倍费用。

## 5. 对正式架构讨论的约束

以下是由实测引出的设计要求，尚未实现，也不是重写一套架构：

- **消息投递、群聊展示和模型唤醒分开。** 收到 mention 或产生群消息不应天然多一次推理；仅在需要新的语义判断时唤醒目标。确定性收件、回执、超时与状态管理交给运行时。Direct mention 仍可保留，不必增加中间模型转述。
- **以有效工作单元调用 Agent。** 同伴收到足够材料后直接产出审查；不为每个状态确认启动一次模型。纯元数据回执不应让整个计划重算。不能以牺牲实际质疑和自主协作为代价机械压低调用数。
- **共享上下文不等于全量群历史复制。** 给每个角色所需证据、版本与变化，利用持久工作记忆和稳定前缀；需要更多材料时按引用获取。
- **启动时裁剪并冻结工具、技能目录。** 一个只审查固定材料的 worker 不应默认承载全套通用开发助手能力。对 Hermes 必须保持会话内提示/工具前缀稳定，工具集变化在新会话边界处理，不能用每轮重建上下文破坏缓存。
- **按协作组预算计量，按收益选择协作。** 聚合 root、peer、重试与恢复的实际用量，同时显示缓存/非缓存输入、输出、调用数。双 Agent 作为按需要选择的模式；难题的质量收益与协调开销需要一起验收。

飞书临时 patch 只解决特定出站文本转原生 at 的问题。正式的 Agent ID、mention 解析、任务授权、协作归属与飞书显示，仍须按架构定义，再决定是否保留这段转换作为兼容层。不能由临时 patch 倒推正式协议。

## 6. 最小复核顺序

先不追加大批付费试验。先固定每个角色的模型、基础指令、技能目录、工具 schema 和版本，并保存可复核的上下文指纹；两组均用可审计的独立会话，使用同样的证据披露方式。必须能拿到每个 root/peer 的逐请求 usage，而非只读最终累计值。

随后选一个有明确协作价值、不会让强单 Agent 轻易满分的固定难题，分别比较单 Agent 自审、一次同伴审查与允许对等往返三种模式。先改变一项因素以分清目录大小、往返次数和任务难度的影响，再扩大任务集。未有新实测前，不承诺优化后会降到某个倍数。
