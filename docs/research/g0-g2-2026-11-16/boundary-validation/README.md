# 消息可审计性与预算边界：验证及补齐

后续小测已完成：[四组调度/上下文对照和抗遗忘结果](../superagent-pilot/README.md)。本页三消息与预算测试保留为前置证据。

2026-11-16。本轮补齐两项证据：**三条真实 Agent 协商正文可独立核对；Codex 原生预算被证实不是严格硬上限。** 因此能够收紧实验与接入契约，但不能宣称已实现独立运行时、正式群聊或月级可靠运行。没有改产品代码、继续OpenClaw/DSH动态验证或向飞书发消息。

## 1. 已验证能力

| 问题 | 证据结论 | 正式接入的边界 |
|---|---|---|
| Agent能否直接交换可读正文 | **通过有限验证**：公开动态工具，原生root/peer三条往返，发送参数=日志=接收结果；peer最终明确回应 | 已找到可审计接入路径；不是原生send_message明文导出，也未验证跨设备 |
| 投递是否等于认可 | **不等于**。探针分开记录发送、返回工具结果、peer明确回应 | 接收回执与接受/拒绝分别记录；“任务完成”另需产物与验收 |
| 父子是否共用预算 | **通过**：父40+子70合计110触发100门槛，两者单独均未达到100 | 仅证实native树；任意独立线程、跨harness或多设备仍需运行时统一归集 |
| 超额后能否保证不执行工具 | **不能**：超额响应所带动态工具已经执行，之后回合才失败 | 预算错误不是副作用阻止保证；外部执行入口需独立授权与额度检查 |
| 超额后能否保证无新模型请求 | **不能**：同turn自动续跑停止，但显式新turn仍请求provider | 宿主必须阻止新派发；仅看回合最终failed不足以证明未计费 |
| 在途请求是否可突破上限 | **可以**：限100，spawn10+两条在途各100=210，超额110 | 这是实测反例，不是最大超额公式；硬上限需要逐请求预留及可兑现的请求上界 |
| 冷恢复是否保留已耗预算 | **未保留，本入口反例成立**：同进程恢复1token仍失败；冷恢复同样1token完成 | 历史可恢复不等于预算可恢复。需独立持久账本及恢复前核对 |
| 原生预算是否为总tokens | **不是**：缓存输入不扣；provider units可优先于fallback加权tokens | 总tokens、非缓存/缓存/输出、原生units和金额分别保存 |

## 2. 对token问题新增的解释

成功三消息探针有8次用量增量，100,110总tokens，其中60,544缓存输入、38,798非缓存输入、768输出。每次输入约1.2万tokens。即使已配置不注入技能目录，spawn、收件、回复、wait及最终回答仍带来模型续跑与重复上下文。费用没有账单，不折算美元。

这给出下一步可检验的假设：**调度引发的模型续跑与上下文组织需要分别检验。** 尚未测量哪种改动可省多少。固定成员是否由宿主启动、首条消息能否随首次执行送入、任务终态能否由宿主事件观察，均为下一轮候选变量；不可直接把全部群消息广播给所有Agent。准备与失败开销也要报告，本轮真实消息探针已知总量下限124,897，失败peer用量不完整，未记零。

## 3. 补齐后的最小契约（要求，不是已实现）

仅明确本轮证据要求的边界，不选数据库、中心部署或扩展完整架构。

**消息与mention：**应保留 `collaboration_id / message_id / sender / recipient / reply_to / body / body_hash / source_kind / execution_ref`。sender由适配器认证的调用身份绑定；正文及群昵称不能冒充人类授权。`execution_ref`指向现有协作步骤；如果是请求新工作，须先经过准入并得到新的执行归属，不能让一个@隐式启动无预算工作。共享协作的账本可属于Collaboration，不强制算为发信者的子任务。本探针仅验证前三条消息链，未实现步骤准入。

**正文、回执与群聊：**记录 `recorded → delivered`，再由具名Agent明确给出 `accepted / rejected / needs_evidence`，不能从前两者自动推导第三者。群聊投影至少显示发信者、收件者、正文/证据链接、回复关系与上述状态，并引用同一message_id。已有飞书文本转at补丁只是渠道适配细节；它不定义身份权威、接受状态或调度权限。本轮没有飞书投影实测。

**预算与恢复：**一份持久的Collaboration账本关联各harness/thread/turn/request及用量来源，分别记录已确认消耗、在途预留、未知用量和恢复状态。宿主看到耗尽后拒绝新的spawn/turn/唤醒；恢复时先核对账本及在途状态，不把新进程的remaining当新额度。拒绝宿主新派发只能约束外部入口，不能阻断黑盒turn里的每次内部模型调用。

**硬预算能力声明：**若适配器不能在每次模型请求前原子预留、约束输入/最大生成与重试上界，并在响应后结算，只能声明软停止门槛及可观察超额，不能声明严格组级金额/token上限。API成本预算与“已授权工具是否允许执行”是两个独立检查；模型响应返回时再发现超额，不能保证响应中的工具尚未执行。未知费用不能视为零或自动释放预留。本轮未实现或验证硬预算方案。

## 4. 下一轮最小验证的顺序

1. **先联合考察调度与上下文。** 后续具体口径见[Superagent验证](../SUPERAGENT-VALIDATION.md)：用四条件区分订阅直通与Inline/Spill的效果，并加入召回正确性检查。此前的控制开销对照仍是其中一部分： 固定模型、资料、三条消息职责与实际工具表，只改变一个控制因素，例如宿主启动固定成员/观察终态；当前8次增量作为参考，不宣称因果基线已完备。先以fixture核验调用顺序，再各一次真实模型记录开销。失败成本纳入。不要同时改任务、成员数和模型后宣称优化倍数。
2. **再做已有候选任务的A/B/C筛选。** 使用可读正文通道、版本冻结、明确宿主停止策略与全组用量；原生budget只作附加保护。首轮只作质量/成本观测，不叫严格等预算实验；若要严格等额比较，先补齐逐请求准入能力。评分和证据包已冻结，不因本轮结论偷偷改变某组资料。
3. **质量出现有效增益后，再推进正式运行时切片。** 优先正文留存、授权/工作归属、外部预算账本与中断/恢复边界，之后再验证群聊与跨设备。当前仍无多Agent质量优势或月级任务达标证据。
