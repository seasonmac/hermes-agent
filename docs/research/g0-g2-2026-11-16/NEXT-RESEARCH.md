## 一、文献改变了什么

1. **不要把“多 Agent 更强/更差”当成通用结论。**《Towards a Science of Scaling Agent Systems》v3（2026-04-08）扩展到260组配置、六个基准，显示收益随任务可分解性、工具交互及协调方式变化。本文的控制包含总推理 token 预算，不等于缓存输入、输出与实付费用完全一致。本项目应同时测任务质量、调用/用量和费用，而非只比较回答分数。不能把早期版本的摘要数字或经验阈值直接作为我们的准入规则。[原论文 v3](https://arxiv.org/html/2512.08296v3)

2. **有 Reviewer 不等于有效验证。** MAST 把失败区分为规格、Agent 间偏差与验证问题；专设验证者仍可能只做表面检查。对应本项目，评审必须交出证据、反例和被修正的判断，不能只输出“我同意”。[原论文 v2，第4.3节](https://arxiv.org/html/2503.13657v2#S4.SS3)

3. **商业经验也要求区分分母。** Anthropic Research 的经验适用于广度探索、多条独立信息线索；其文章给出的约15倍消耗以普通聊天为基准，不是相对于我们的强单 Agent。它支持按任务价值选择协作，不支持拿一个公开倍数替本地预算验收。[官方工程文章](https://www.anthropic.com/research/multi-agent-research-system)

以上是研究依据；下面的场景、比较条件和架构方向是本项目的提案，尚未成为生产实现或用户选定的技术方案。

## 二、最小场景：方案与反例的直接协商

建议从一个有真实资料的工程任务起步：**审查 Hermes/Codex 的统一接入承诺，在重复投递、忙时输入、取消及恢复时给出可兑现的最小契约。**

交付 Owner 提出方案，验证者独立构造反例；双方可以直接请求证据、反提案、拒绝无依据判断。Owner 负责产物，不具有把分歧写成共识的权限。单 Agent 条件拥有同样全部证据并承担自审职责，不能人为少给它资料。这个场景用于发现协作能否产生有效修正；尚不知道难度是否足够，不能预言一定出现收益。

任务来自当前真实接入问题；资料为此前运行观察、原生轨迹和对应说明，已复制并记录SHA-256，避免试验途中被文档更新污染。任务中的错误候选承诺是审查材料，不代表系统现有设计。

交付物：[任务](next-pilot/TASK.md)、[评价和预检](next-pilot/EVALUATION.md)、[证据清单](next-pilot/manifest.json)。本轮尚未运行该任务的质量对照。

比较保留三种条件：A单 Agent 自审；B一次同伴审查；C有界直接协商。这样可以区分“多一份审查”的收益和“额外往返”的收益。第一轮只用于筛选，若单 Agent 已达到评分上限且协作没有新的有效反例，就停止在此题上重复消耗。月级任务不由这份短测代替验收。

## 三、配置校准：已有实际结果

**此前“提示不要使用技能”没有去掉目录。** 实装接受 `skills.include_instructions=false`；`skills.enabled=false` 反而是未知字段。插件总门为 `features.plugins=false`。只使用 `--ignore-user-config` 不能保证注入环境相同。所有设置只用于独立诊断进程，未更改用户全局配置。[完整核对](FROZEN-HARNESS-NOTES.md)

本轮只跑了一次主 Agent 创建一个同伴、等待其返回的短校准：

| 模型用量增量次数 | 3 | 1 | 4 |
| 输入 tokens | 35,769 | 11,380 | 47,149 |
| 缓存输入 | 23,552 | 0 | 23,552 |

| 总 tokens | 35,871 | 11,387 | **47,258** |
| 自动技能目录块 | 0 | 0 | 0 |

35.62秒完成，root输出ROOT_OK，peer输出PEER_OK。两者基础指令hash一致。root首次输入11,831 tokens，peer首次11,380；两者仍有通用助手基础指令和工具说明，所以清除技能目录并不消除固定开销。没有把这项简单任务与旧G2复杂任务直接相除，不能宣称已经得到某个性能优化倍数。

完整工具schema的hash不同，核对后发现root多两个面向用户的异步交互工具；其余schema剔除这两项后hash一致，这两项未被调用。该差异应成为预先声明的角色差异，而非悄悄忽略。[用量与上下文观察](calibration-v2/observation.json)、[工具差异](calibration-v2/tool-surface-audit.json)、[配置](calibration-v2/settings.json)、[运行事件](calibration-v2/events.jsonl)

**预算仍不能写成严格总 token 上限。** 实装接受旧 `limit_tokens` 配置，不接受本地新源码中的 `limit_budget`、`reminder_at_context_start`。当前源码的预算可能采用provider units，fallback则按非缓存输入/输出权重记账；初次校准只验证配置被接受和预算提示出现，未触发耗尽；root与peer都有预算指令块。后续[实装边界测试](boundary-validation/budget/README.md)已证实共享扣费，也发现同turn自动续跑会停止，但显式新turn仍发请求、超额响应内工具已执行、在途总量可到210/100、冷恢复重置预算。因此不能描述为统一关闭所有新工作入口，更不是已通过的硬预算保证。

## 四、对架构讨论的直接影响

优先比较两个方向，而不默认把所有Agent都持续唤醒：

- **固定控制流程 + 按需协商窗口（当前建议）。** 任务阶段、允许角色和预算由运行时约束；Agent在允许的协作范围内自行找同伴、质疑或交接。无语义判断的收件、回执、计时和记录由程序处理。
- **持续共享群讨论。** Agent持续追踪群内变化，自行决定是否参与。灵活性更高，但唤醒、重复上下文、来源权限及停止传播都更难限制；当前没有足够质量/成本证据支持把它作为默认。

这不是决定中心部署还是对等网络；通信拓扑、模型协作关系、任务授权是不同选择。首个方向也不要求所有消息经一个中间模型转述，更不要求把所有协作都变成委派树。

正式设计接下来必须把五个边界写清：

1. **mention不自动等于新工作。** 对已有协作的回复、新工作请求与仅供共享的证据应可区分；产生执行时必须有明确归属与额度。
2. **共同协作可以共享预算。** 不应强制把对等协商都算成发起方的子任务。群里能看到谁向谁提出什么、谁接受或拒绝，但展示本身不应启动新模型。
3. **共享状态有证据和接受者。** 运行时保存提案、依据、接受/拒绝及版本；不能以“已投递”替代“已读/理解/认可”，也不能让每次更新都启动额外治理Agent。
4. **工作流控制阶段，Agent决定阶段内的语义行动。** 动态生成脚本与直接协商应共享执行归属、恢复记录和预算；尚未选定具体API或存储产品。
5. **长期进展由有效产物衡量。** 应记录验收条件完成、证据变化、错误修正、阻塞解除和未决风险；消息数量、活跃Agent数、运行时长都不是进展。下一段脚本、目标变更与人工介入必须有触发条件。

飞书patch只提供临时文本→原生at转换。Agent身份、消息授权与协作语义由正式架构决定，再选择patch如何迁移；不能让现有字符串替换逻辑成为领域协议。
