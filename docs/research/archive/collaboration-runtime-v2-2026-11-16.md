# 独立协作运行时设计 V2：工作归属、认知治理和长程质量

2026-11-16。设计修订稿；没有产品代码、部署或实际通知配置。本文替代 11-15 草案的执行归属、知识接受、依赖追踪、持久化、人工治理与阶段验收章节。六种模式、独立模块、Router、直接 mention 和跨 harness 的方向保留。旧稿灾备架构不构成首版要求。

## 1. 修订决定与边界

首版采用一个逻辑控制服务、一套 PostgreSQL 权威状态与 journal、分布式 Node Daemon、两个先行 harness adapter。暂以 Hermes 和 Codex 为集成候选，具体公开接口在适配阶段核实。OpenClaw、DSH 使用同一契约逐步接入，不预设尚未审计的能力。

本轮取舍：采用用户建议的轻量持久化方向；保留调用结果复用，但将事件、预算、执行身份也纳入同一 journal 事务。移除 Temporal，不同时维护另一套工作流权威。工作流全静态会限制协作；完全自由聊天又缺少工作归属，因此采用“固定目标与验收边界 + 可登记的动态子步骤”。

一个月的首要成功条件是持续产出有证据的有效进展、修正错误并保持目标，而非进程存活。首阶段必须与相同预算的强单 Agent 对照；协议正确且质量无收益，不足以进入月级建设。

推荐但未经用户确认的默认值：单组织信任域、逻辑集中控制、PostgreSQL、每日摘要与每周复核的产品选项、下文无进展阈值。本文没有创建任何通知或自动化。

## 2. 统一执行模型：脚本和 mention 都只能产生登记过的工作

核心对象：Mission（目标与总预算）→ Collaboration（一次协作范围与责任）→ Step（工作单元）→ Attempt（执行尝试）。Workflow 是 Collaboration 内的一种计划来源；事件也可生成 Step。所有模型调用，包括路由分类、审查、回复、重新规划与摘要，都必须归入 Step；纯传输不调用模型。

Step 新增：origin=workflow|message|human|timer|governance，caused_by，parent_step_id，collaboration_id，sponsor_budget_id，required_for，contract_version，context_snapshot，state，result_ref。Workflow Step 另存 revision/call_key；消息 Step 另存 request_id/recipient_id。恢复与预算挂在统一 step_id/attempt_id 上，不再只挂在脚本 stepKey 上。

### 2.1 可自由选收件人，执行必须经过准入

mention 是地址，不是执行授权。A 可直接 @B，不经协调者 LLM 转述；服务只校验身份、上下文可见性、工作范围和额度。Workflow 为每个 Collaboration 声明 collaboration_policy：允许请求哪些能力、共享范围、可用协作额度、最大深度/并发、截止时间、哪些结果须汇合。

没有脚本的群聊同样是正式入口：Mission 创建时登记一个默认 reactive Collaboration，绑定 Room、责任 Agent、目标版本和从 Mission 授予的协作额度，policy 来自 Mission Owner 的授权模板。人类直接 @ 或授权 Agent 主动发起请求时，优先选当前话题绑定的开放 Collaboration，其次选择该默认范围。只有现有授权允许时才创建新的协作范围；找不到唯一 Mission 或足够授权时暂存请求并要求明确归属，不先启动模型。关闭的范围不会被迟到消息自动重开。后续需要复杂控制流时，可在该范围提交 Workflow，已有请求身份和消费不改变。

| 消息类别 | 是否生成工作 | 归属与作用 |
| --- | --- | --- |
| inform / 已有请求的 reply | 默认不新建 Step | 入 inbox，按绑定点注入；若需模型主动分析，先登记一个 Step |
| request（求助、调查、审查） | 创建 reactive Step | 默认挂到发起 Step 所属 Collaboration，预算由请求方所在协作范围承担 |
| scope_change_proposal | 创建或复用规划审查 Step | 未接受前不改变主流程或成功条件 |
| 人类直接 @B 提出新工作 | 准入后创建 Step | 群聊绑定的 Mission；归属不明确则要求选择，不能挂任意预算 |

请求的唯一身份为 mission_id + request_id + recipient_id；request_id 在发送端首次操作时持久生成并在重试中保留。一个请求指向多个 Agent，每个接收者有自己的 Step。内容相似不是可靠去重依据；恢复后的模型若重新构造不同 request_id，系统不能保证语义去重，适配器必须回放已提交工具回执，额外请求仍受额度与深度限制。

一个事务写入消息、reactive Step、预算预留与派发 intent；拒绝准入时消息可见但不启动工作，显示原因。parent_step_id 表示因果关系，不重复扣钱；共享预算账本聚合子步骤消费，子额度从父范围转拨，不能父子各计一次总消费。

### 2.2 谁控制下一步

脚本控制阶段门、必需产物、汇合和验收。Agent 在协作策略内决定找谁求助、如何调查；不能靠 @ 修改目标、跳过审查或扩大预算。六种模式仍可包含这些动态子步骤。

默认 request 是发起 Step 的 required child。父 Step 可以记录候选结果，但只有必需子步骤已解决或按既定策略明确失败处置后才能被接受。关闭协作范围与新建子步骤在同一事务边界检查，关闭后到达的请求被拒绝或进入新范围，不能绕过汇合屏障。

可选支线需要显式标为 optional，设独立额度和截止时间；父 Step 完成时默认取消尚未结束的可选支线。需要继续时必须显式提升到仍开放的 Collaboration，保留费用与归属；禁止隐形后台工作。Mission 结束前每个支线都必须完成、取消或明确处置，未知操作不会被消失处理。

修改依赖、主路径或验收条件要提交 workflow revision proposal。范围内的执行策略调整可由受授权的 Mission Steward 接受；目标、禁止项和总预算改变由人批准。提交新版本后旧执行结果保留，但仅在明确复验后复用。

批准目标变更时，在同一事务更新当前有效 contract_version 和受影响工作的准入屏障。否决提案时，在同一事务更新该提案及其依赖工作的准入状态，不改动整个 Mission 的目标版本。对于目标版本切换，默认阻止所有旧版本排队工作启动、阻止旧版执行新建子步骤；能够证明不受影响的工作，经显式版本映射后继续。运行中的受影响工作请求停止或在安全边界落盘；迟到回复、完成回执、外部结果与费用继续记账，但不会直接唤醒业务后继或满足新验收。只有经当前有效版本复验/重新授权的结果才能推进后继；对账和收尾仍可运行。被否决提案派生的排队/重试工作受同样检查，批准其他对象不会复活它。

### 2.3 B 忙碌、回复与恢复

独立 request 默认排队到 B 的新轮次，在自己的 reactive Step 下执行，不偷偷计入 B 正在做的另一项任务。不相关任务不混入同一轮。与 B 当前请求明确相关的 reply/inform 可以在安全边界加入已有 Step，绑定本次输入快照和 journal 序号，恢复重用相同输入。

同一 session 一次仅运行一个 turn；等待回复时落盘检查点并释放执行槽。若 harness 无法释放后恢复，使用接力会话或返回受限能力，不能让 A/B 互相占着唯一槽等待。wait-for 环路触发显式阻塞事件，按预设责任策略处理。

回复只形成候选结果；原请求的验收契约决定 resolved。消息不重新唤醒已解决请求。恢复时查原 reactive Step：完成则复用结果，运行则重新绑定，状态未知则对账，未启动才派发。取消沿必需子步骤传播；再次执行必须属于明确重试 Attempt。

例：A 在工作流 Step S 做市场分析，@B 核对一家公司的收入来源。运行时创建 T，parent=S、sponsor=同一协作预算。A 等待，B 在 T 内取证并回复。T 的产物通过证据检查后 S 继续。服务此时重启只重新绑定 S/T，不把 @B 再执行一轮。B 请求 C 的后续调查也是同一树中的新 Step。

## 3. 共享上下文：指定接受权，区分事实与可用判断

将旧 Accepted State 拆成“验证记录”与“当前采用的判断/决策”。accepted_for_use 意味着在明确范围、版本和有效期内可供后续工作使用，不表示客观真理。certainty 与 usage_status 是两个字段；模型自报置信度不能代替证据。

每条知识记录：claim、类型、来源、适用范围、支持与反对证据、不确定性说明、作者、审查者、接受者、policy_version、有效期、下游用途、复核触发条件。每个领域在 Mission 启动时绑定具体 Agent ID 与权限范围；不能仅写“由专家接受”。角色可以由具名 Agent 承担，重要结论的作者和审查者不能是同一个 Agent。

| 知识类型 | 谁接受 | 接受依据与限制 |
| --- | --- | --- |
| 数据/实验/构建记录 | 证据检查器，异常交领域 Reviewer | 固定数据/代码版本、运行回执与可复现性；只确认记录或测量，不自动推出理论正确 |
| 外部事实性主张 | 领域 Reviewer | 可定位原文、日期、口径、来源可信度；高影响主张需原始证据或独立核验；转载不能算独立来源 |
| 市场解释/预测 | 研究 Owner，须有独立 Reviewer 意见 | 证据覆盖、替代解释、反证、时间与地域边界；接受为工作判断，非 verified fact |
| 量化研究结论 | Quant Research Owner + 独立方法审查 | 数据版本、泄漏检查、预定评价方法、成本假设、样本外或其他适用证据；缺关键材料保持 conditional，不写成已验证有效 |
| 工程实现结论 | Engineering Owner + 验收检查 | commit、行为验证和接口合同；测试通过不能外推所有性质正确 |
| 可逆执行策略 | Mission Steward | 在已授权范围/额度内，记录方案权衡、回退条件与依据 |
| 目标、禁止项、总预算、权限扩大 | 人类 Mission Owner | 版本化变更提案和影响说明 |

Memory Steward 只负责整理、检索、去重和发起复核，不自动获得上述接受权。Reviewer 也可以错，所以必须保留异议和审查依据，而非以“多数模型赞成”作为唯一证据。

状态：proposed → under_review → accepted_for_use / conditional / contested / rejected；后续可变为 stale / superseded。conditional 可以在允许风险的探索分支中使用，输出必须继承该条件；不能被摘要抹成事实，也不能满足禁止条件性证据的最终 gate。

日常结论由具名 Agent 角色接受，不逐条请求人类。重要分歧先补证或进行一次有界独立复核；仍会改变关键决策且无法按既定规则处理时才升级给人。升级前可继续不依赖争议的工作。采纳、否决和撤销均有不可变 decision receipt。

## 4. read_set 的真实边界

旧稿对可追踪性的承诺过强。对不透明 harness，运行时能证明注入了什么，不能自动证明 Agent 读过的所有文件、网页和数据库。

每个结果必须携带 dependency_coverage：

| 等级 | 来源 | 可以承诺什么 |
| --- | --- | --- |
| enforced_scope | 关键输入只能经受控数据接口/固定工作区读取，旁路受执行环境限制 | 在声明的受控输入范围内传播失效；不声称捕获模型预训练知识 |
| observed | 适配器工具事件能记录部分读取 | 对观测到的依赖传播，可能漏掉 shell、脚本内部或未上报的读取 |
| declared | Agent 自报引用与 manifest | 可审查线索，不是完整依赖证据 |
| opaque | 仅知道注入内容 | 只能保守地作范围级复核 |

所有注入依赖由运行时记录；工具观测依赖、Agent 自报依赖分别标记来源，不合并成看似完整的列表。使用一个受控工具不等于所有读取都受控，只有禁用/隔离旁路后才能声明 enforced_scope。

关键数据采用版本化 dataset、Git commit、抓取快照与 artifact 引用，尽量避免可变 live URL 和本地路径作为唯一依据。无法限制读取的 harness 可以探索，但其关键结论进入受控验证 Step 后才能满足严格证据 gate。

变化传播只保证覆盖已记录依赖。遇到关键数据更新且覆盖不完整，按 dataset/workspace/主题范围将相关产物标记 needs_revalidation；不能因 read_set 没命中就宣称仍有效。范围也不清楚时复核该里程碑，必要时整个 Mission；原产物保留。

handoff 和摘要只做索引，不替代原始证据。接受的结论应关联来源本体，避免一个月内反复“摘要的摘要”造成证据损失。

## 5. 目标漂移、错误累积与进展治理

Mission Contract 固定：目标、排除项、成功标准、证据门槛、预算、时限、允许自动调整的范围。每个 Step 指向具体目标/待决问题，重新规划也要说明如何改善它。人类改目标生成新版本，保留旧目标与已发生成本。

设立 Mission Steward（可为 Agent）负责计划维护，独立 Progress Reviewer 检查证据和偏离。二者调用同样登记为治理 Step 并计费，不能形成无限管理层。建议首版以阶段边界或每日一次为检查触发，运行频率和人类通知频率分开。

每次 progress checkpoint 保存：目标版本、验收项变化、新证据、已排除假设、当前异议、剩余阻塞、消费、下个可检验预期。进展至少分三种：交付进展、知识进展、健康状态。心跳和消息数量只证明活跃；否定一个假设可以构成知识进展。

| 领域 | 有效进展证据 | 不可单独作为进展 |
| --- | --- | --- |
| 软件工程 | 新行为通过验证、复现并定位故障、集成风险下降 | commit 数、代码行数、Agent 自报完成 |
| 量化研究 | 预定实验完成、排除候选解释、识别数据缺陷、复现结果 | 只挑最好回测值、不断改指标追逐结果 |
| 市场调研 | 关键问题的独立证据覆盖增加、矛盾被澄清、结论边界更明确 | 搜索次数、引用数量、报告长度 |

建议默认：连续两个有实际验收或取证机会的检查窗口无新增有效证据，启动一次有额度上限的诊断；长实验按预定中间里程碑判断，不因一天未结束误报停滞。诊断只能选择补证、换方法、缩小范围提案或升级；诊断后的观察窗口仍无进展，则停止相关分支并请求决策。目标达成必须由验收 receipt 证明。

防错误累积：关键结论进行独立审查；每日抽样重查已采用主张；重要行动前复验其核心前提；摘要保留 uncertainty 和原始引用。抽样频率与阈值由领域 policy 配置。发现早期错误时使其下游结论失效，重新开启受影响验收项，已完成项允许回退，不能只增加“完成百分比”。

目标漂移检查比较当前工作与当前有效、经人类批准的完整 Contract 原文，不只读最近摘要；同时显示它相对初始目标的授权变更记录。运行中不得自行降低成功标准；进展慢可以提出改目标，但不能自己把目标改容易然后宣布成功。

## 6. 人类在群聊中的一等角色

人类角色：Mission Owner 有目标/额度权限；Domain Approver 在授权领域作接受决定；Observer 只读。角色绑定认证账户，Agent 发来的“用户说可以”不等同用户授权。

群聊提供以下操作契约，首版可为文本命令或操作卡，不依赖特定聊天平台：

| 操作 | 记录与执行 |
| --- | --- |
| 批准/否决提案 | 指向 proposal_id、版本与作用范围；版本变更后旧批准不能套用 |
| 修改目标/约束 | 展示目标差异、受影响步骤与已发生成本，提交新 Contract revision |
| 暂停/恢复/终止 | 停止新准入，显示仍在进行和不可立即停止的外部操作 |
| 纠正一条知识 | 发出 correction，引用原 claim，触发失效与复核；偏好指令与事实判断分开 |
| 分配/减少预算 | 修改预算合同；不能追回已花费用，低于已承诺额度则阻止新工作并显示未结部分 |
| 要求解释或重规划 | 形成治理 Step，给出证据、方案和成本影响 |
| 直接 @Agent | 创建有归属的 request，可观察其工作与费用 |

自然语言如“好”只能在唯一明确、仍有效的提案上下文中解释成批准；多义时展示待确认对象，不猜。发起审批时展示可审阅的具体成果，而非笼统问“是否继续”。人类决定和 Agent 提案均进入同一 journal，审批等待可恢复。

建议的产品通知策略，尚未为用户启用：每日一份摘要，包含新增有效成果/反证、目标偏离、争议、消费与剩余预算、下一阶段、需要人的决策；每周提供里程碑复核包，无目标/风险变化时可只读，无需例行点击批准。严重错误、越过授权边界的需求、预算不足以完成必需工作、持续无进展立即通知。信息合并、去重并遵守用户静默时段；关键阻塞规则单独配置。

每条人工决策请求有期限和超时策略：默认暂停依赖该决定的分支，继续独立且已授权的工作；不响应不是批准。需要扩大预算/权限、变更目标或存在不可处置外部操作时，不能由超时自动放行。最终验收可按预授权机器标准自动完成；指定 human-signoff 的交付物等待人批准。

## 7. 首版持久化：单一 PostgreSQL + journal + 结果复用

只有一个运行权威库。journal 记录命令、外部事件、调用开始/完成、消息、决策和状态变更；step/message/budget 等表是同一库的业务状态，必须与对应 journal 事件在同一事务提交。产物正文可存文件/对象存储，通过 hash 引用；它不是另一套调度权威。节点本地 journal 是可重传的执行回执，不可离线裁决全局状态。

调用缓存身份：run_id/revision + call_key，加已登记的上下文、参数、权限和产物指纹验证。同一版本确定性重放消费相同事件和保存结果；首次输入不一致时停止沿用旧后续调用，创建新版本并显式映射可复用成果。不要把旧副作用作为缓存失效后的普通调用重做。并行项目使用稳定 item key，避免启动顺序变化把结果错配。

消息触发工作用 request_id 派生的 step_id；timer 和人类决策使用已登记 event_id。脚本恢复消费 journal 中同一事件，不能重新查询“现在有什么消息”替换原输入。纯函数可重算；所有对外可观察效果、等待和模型结果都必须登记。第一版没有任意网络/文件/随机源的脚本旁路。

最小调度器只负责：扫描可执行 Step、到期 timer、未投递 intent，领取并派发；不另建复杂引擎。数据库唯一约束/CAS、单 session 活动 turn、租约和 attempt_id 保留，用于重复投递与正常崩溃恢复。完成事务写结果引用、状态、预算结算与后继唤醒；重复完成幂等，未知费用继续占用并标记估计。

跨设备副作用保留最小 operation intent/receipt。派发之后结果丢失时 inspect/reconcile，不能依靠“无缓存结果”推断“未执行”。只有支持所需幂等/检查能力的 adapter 能获得相应保证；不能用一张 journal 表推导任意外部动作 exactly once。

灾备回滚、跨控制域、自动故障切换与 control_incarnation_id 体系移出首版。首版灾备恢复后若可能丢失已提交执行记录，明确禁止自动重派，人工核对后恢复；不承诺零数据损失或自动灾难恢复。完整灾备仅在真实部署需求出现后单独设计。

## 8. Router、六种模式与 adapter 的修订接口

Router 保留地址解析、能力选择、节点放置、上下文选择；新增依据 collaboration_policy 校验请求资格，但不改写内容、不替 Agent 决策。显式 @ 对象不被静默替换。盲审 ACL 同样约束 Agent 间 mention，不能靠私聊绕过上下文隔离。

六模式保持 classify-and-act、fan-out-and-synthesize、adversarial verification、generate-and-filter、tournament、loop-until-done。每种模式都使用统一 Step 账本，并继承同一知识接受与进展政策；未知结果不当失败/成功证据，预算耗尽不当达标。Tournament 的 winner、top-k、全排序是不同合同。

adapter 原有 session、startTurn、input、events、inspect、interrupt、checkpoint、resume、usage 接口保留，新增/明确：执行归属 envelope（step/attempt/预算/合同版本）、协作请求工具回执持久化、输入绑定序号、provenance 能力等级、原生子 Agent 清单/可控制范围。无法枚举的原生子树只视为一个有界活动，不能假装每个子 Agent 已进入统一治理。

原生模型调用、辅助调用、隐式委派的预算能力必须声明 enforced 或 observed。若无法强制请求级预算，允许按可验证的有界轮次准入；仍无法界定则只提供软预算并排除要求硬上限的任务。恢复只由一个 recovery_owner 驱动。

## 9. 第一阶段就验证协作质量

首阶段交付是“可比较的协作任务闭环”，不是纯协议演示。先两个 harness、两台设备，但不要求先做齐四种 adapter 或六种模板库。

对照建议：A 为强单 Agent，可用同样工具、上下文资源、持久会话和自审预算；B 为多 Agent 工作流；C 在 B 上开启对等 mention，用来检验 mention 的额外价值。共享证据服务对 A/B/C 一致提供。模型配置和资源记录清楚，避免把工具/模型差异误当协作收益。

先做 12 个代表任务试验（软件、量化研究、市场调研各 4），配对重复至少 3 次作为可行性探测，不据此宣称统计证明；后续样本量依据观察方差与目标效果确定。开始前锁定任务、成功标准、预算/时间上限、人工帮助规则、评审 rubric；评审尽量盲化并由领域判据或人类抽查校准，不能只让另一个 LLM 自由打分。

比较有效成果质量、关键错误、预算内完成率、总成本、完成时间、人类修正时间；记录分领域结果，不能用一个领域收益掩盖另一个领域退化。额外开销包含规划/路由/评审/聊天/恢复。相同总预算下比较质量，并报告质量—成本关系。

本稿推荐推进标准：至少目标任务类别中出现可重复的实际质量或效率收益，且关键错误和人工负担没有不可接受增加；具体最小有用提升在实验前由产品目标确定。若 pilot 不确定就补样本，不直接进入月级工程；若某类任务无收益，默认单 Agent，Router 仅把适合任务升级为协作。

首阶段还必须注入：中途关键证据反转、执行中用户改目标/否决、一次重启、一次迟到 mention，观察能否修正而非沿错误继续；验证旧完成回执仍入账但不会启动被否决的后继。另覆盖一条完全无脚本的群聊 @ → 默认 Collaboration → reactive Step → 回复 → 重启复用路径，避免只实现脚本内求助。长期效果另用 72 小时、7 天、30 天任务逐级验证；短任务的质量收益不能证明一个月不会漂移。

首阶段协议验收：所有 @ 触发调用可追到 Step 与费用；重复投递不重复新建工作；停机后已完成请求不重做；未观测依赖不伪称完整；条件性结论不能变成确定事实；人类否决不会被回复/重试绕过。质量与协议必须同时通过。

后续次序：六模式扩展与进展治理完善 → 更多 adapter 与故障矩阵 → 7/30 天运行、保留/升级 → 按需要增加高可用与灾备。首版不以灾备组件数量衡量成熟度。
