# 004 Prompts：让每次执行读懂当前工作

上下文设计的目标，是让 Agent 知道当前要解决什么、哪些证据可靠、何时应停止。省 token 要建立在这些信息完整的基础上。运行时负责授权和状态，提示词负责把工作解释清楚，两者不能互相替代。

继续市场研究示例：A 检查统计口径时，应直接看到当前问题和两份资料的关键片段，而不是先读整个月的群聊。只有需要追查细节时，才读取长报告中的相关部分。

## 角色职责保持简单

| 角色 | 需要的输入 | 应交出的结果 |
|---|---|---|
| Lead | 当前合同、检查点、证据变化、未决问题和可用额度 | 下一阶段提案，或需要人作出的具体决定 |
| Worker | 当前 Step 合同、关键证据、可联系成员和权限范围 | 产物、依据、未知项、补证请求或等待说明 |
| Reviewer | 固定产物和证据快照、明确审查问题 | 可复核异议、缺少的证据或接受建议 |
| Router | 原始请求、已知负责人、候选成员能力与任务归属 | 路由建议、理由或仍需澄清的信息 |

同一 Agent 可以在不同 Step 承担不同职责，但当前身份、权限和费用归属必须明确。Reviewer 的职责是审查指定问题，不默认重做全部任务。记忆整理与进度检查按需开展，不设置常驻 Memory Steward 等额外管理层。

## 何时需要模型 Router

明确 @B、已有请求负责人的后续消息、回复和已绑定事件，都由程序直接寻址。内核切片遇到归属不明时，请人澄清。完整首版才在 Mission 和费用授权已知、成员归属仍不明时，登记一个有额度上限的路由 Step。

Router 输出原 `request_id`、建议成员或协作范围、工作归属、简短理由及缺少的信息。程序再完成准入；原文始终保留，路由摘要不替换人的需求。Router 不承担技术规划，也不负责猜测一个未知 Mission 的授权。

DSH 原型的能力卡、短说明和批量路由提供了参考，但其中 20 条、30 词或 160 字符等数值不是本项目验证过的最优参数。完整首版应按实际输入预算设限，并区分“负责响应”和“只接收上下文”。

<a id="context-packet"></a>
## 一份执行上下文怎样组织

每次获准执行，都有一份可追溯的输入集合。面对 Agent 的内容按以下顺序组织，让它先理解约束，再处理证据。

1. **稳定职责。** 说明当前角色、工具能力和执行边界；这些内容在会话建立时固定。
2. **当前控制事实。** 给出完整有效目标、成功标准、禁止项、暂停状态及合同版本。
3. **当前工作。** 解释本次 Step 要交付什么，附关键短证据、待决冲突、接受者和停止条件。
4. **可继续查阅的资料。** 给出较长资料的索引、版本、适用范围和读取入口。

任务卡、摘要和恢复卡只作为入口，标出来源、版本、生成时间及局限。无关群聊、他人的完整会话和重复工具输出不默认进入上下文。

索引项应包含 artifact ID、hash 或版本、主题、长度、适用范围、可用性和访问方式。读取后返回原文位置及所读版本；来源变化或不可读时，显式报告变化或 `unavailable`，不把旧摘要当作刚读到的数据。

`read_set` 标明运行时注入、适配器观察、Agent 自报或内部不可见。只有关键资料被强制通过受控入口读取时，才能将相应范围标为 `enforced`。重要验收前重新核验来源，不能以“没有收到过期通知”证明资料仍新鲜。

<a id="context-evidence"></a>
## 内联与按需读取怎样选择

短且必读的证据通常直接放进输入；长而低相关的资料适合提供索引，让 Agent 批量读取需要的部分。这是成本与可靠性的共同选择：外置读取减少重复长文本，也可能增加一次工具往返和漏读风险。

[长资料小测](g0-g2-2026-11-16/superagent-long-pilot/README.md)给出了以下实际记录：

| 合成低相关资料规模 | 全文内联总 tokens | 按需读取总 tokens |
|---|---:|---:|
| 32 KiB | 16,689 | 22,882 |
| 96 KiB | 27,301 | 22,866 |

该结果支持混合策略，不能推出通用的 32～96 KiB 阈值或账单金额转折点。选择时还要看必读比例、复用次数、读取往返、缓存情况和新鲜度。每种策略记录总 tokens、缓存分项、延迟及召回错误，再调整默认值。

[四条件与基础召回](g0-g2-2026-11-16/superagent-pilot/README.md)共记录 283,190 tokens；长资料与无预警召回共 8 个样本、186,885 tokens。静默过期和未预告断链的预设检查通过，支持关键事实主动核验、缺失保持未知。每条件小样本、合成资料、缓存冷热未控制及非独立盲评等局限仍然存在；它们尚未证明真实压缩或月级记忆可靠。

<a id="session-reuse"></a>
## 保留缓存，也明确何时换会话

会话启动时先确定实际生效的模型、角色指令、skills、工具表和权限，并记录配置与输入规模。之后通过追加消息或证据引用更新工作，不静默改写历史前缀。Hermes 的提示缓存依赖这种稳定性；每轮重载记忆或重建工具表会增加消耗。

“合同版本变了”本身不足以决定是否换会话。运行时先判断这次变化与原工作是否兼容：

| 变化 | 会话处理 |
|---|---|
| 补充说明、相同目标下的证据更新、相容的阶段变化 | 可以续用，追加完整有效控制事实及版本，明确旧信息的适用状态 |
| 目标方向、成功标准或当前角色职责实质改变 | 对账旧 Attempt 后建立新会话，以新合同和必要历史证据恢复 |
| 工具、权限或稳定角色指令改变 | 按 harness 的会话配置边界重建；内核切片不在原会话中途切表 |
| 旧会话确认不可恢复，或到达合同约定的轮换点 | 新建绑定并加载恢复包；原工作、费用及未决项保持关联 |
| 无法判断兼容性 | 先暂停该工作并澄清，避免在含糊目标下继续执行 |

续用时，旧目标属于历史，新输入明确指出当前有效版本。工具动作和产物验收仍由程序按有效合同检查，不以模型口头确认代替授权。新会话也不能消除旧 `unknown`；原执行必须先满足 [003 处置条件](003-execution.md#unknown-disposition)。

同一工作收到回复时，若角色和配置仍兼容，优先续用会话。新成员默认使用最小必要上下文；只有实际证据表明继承历史有益时才采用 fork，并分别报告缓存命中和总输入。原生压缩遵循 harness 机制，记录费用、绑定变化和恢复限制，不迁移私有推理或声称保留 KV 状态。

## 工作输入和结果怎样写

一个 Worker 合同应能直接读懂：本次要交付什么，完成标准是什么，可以读哪些证据，仍缺哪些信息，允许联系谁，何时停止，由谁接受结果。结果应把观察、推断和待验证内容分开，给出可定位的来源。

| 结果类型 | 必需内容 | 程序怎样处理 |
|---|---|---|
| Lead 阶段提案 | 合同和计划基线、Step 与依赖引用、成员、交付与验收要求、额度、期限和有限下一动作 | 按 [003 阶段流程](003-execution.md#flow)校验，接受后登记执行意图 |
| Router 归属建议 | 原请求、候选成员或范围、理由和不确定项 | 程序检查归属与权限，随后决定是否准入 |
| Worker 回报 | `completed`、`waiting`、`needs_evidence`、`blocked` 或 `declined`，以及产物、来源、未知项和下一条件 | 结合原生终态更新 Step；`waiting` 必须说明所等 request/event |

这些是运行时要实现的输出合同，不假设 harness 已有同名协议。格式错误记为未交付合格结果，按合同限次修正并计费。文本中的 `completed` 表示 Worker 声称已交付，不直接产生 `verified`。

Worker 可以直接请求同伴。消息工具保存请求并返回持久回执；等待交给运行时，Worker 随后结束回合。正常工具返回后仍可能需要一次模型续跑，因此费用按实际请求统计，不额外要求 READY、收件确认或重复状态汇报回合。

## 恢复时给 Agent 什么

恢复包首先解释当前目标和授权，再给出已采纳产物、未决异议、失败路线及原因、关键来源、未完消息、预算和下一项验证。Agent 先核验重要资料，再判断下一步。恢复包不要求重新阅读整个月的对话，也不把过去每条操作重新执行一遍。

向人提问时，提交带对象和版本的具体提案：问题、选项、后果、推荐项、影响范围、截止以及是否阻塞。重复问题更新原提案，人的答复绑定当时版本；确认和否决的语义以 [002](002-authorization.md#human-control)为准。

## 提示约束与真实权限分别验证

网页、仓库文本和同伴消息作为来源数据呈现，其中的角色伪装不获得控制权。实际隔离依靠工具派发、账号和环境权限。T0-P 已表明“工具表更小”与“所有执行路径都被限制”不是同一项能力，配置细节见 [007 实测适配](007-architecture.md#adapters)。

提示调整前检查是否改变缓存前缀、实际工具、输入规模或实验条件。对照组保持模型、证据、权限、skills 和预算一致，统计规划、路由、压缩、评审、续跑及失败消耗。先取得有区分度的小样本，再决定是否扩大验证。
